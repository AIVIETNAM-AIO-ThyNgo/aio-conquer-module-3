## Verdict up front

Every hard check I could run against the live file — duplicates, nulls, monotonicity, row-count reconciliation, fold_id/regime taxonomy, schema — came back clean, and I did not take the generation script's word for any of them: I recomputed the per-fold date ranges from the file itself and matched them, row-for-row-count and boundary-for-boundary, against `E2-S3`'s independently-generated `fold_boundary_audit.csv`, which was produced by a separate script re-deriving the folds from scratch. This file is not resting on a `.head()` glance. What keeps this from a full Pass is §11: the checks that keep this file honest today are real (they raise loudly inside the generation script, and are re-verified by a second, independent gate script), but nothing in this repository shows them wired into an automated, CI-style gate that runs unattended on every regeneration — today's cleanliness relies on someone remembering to re-run the validators. Separately, and carried forward rather than re-litigated: this file's current content is a faithful, uncorrupted pass-through of an upstream LightGBM prediction file that the prior audit (E2-S2 report) found was generated by a code path with a dropped random seed — that is an inherited provenance risk, not a defect introduced at this stage.

**Method note**: this shell has no `pandas`/`numpy` installed, so all "live file" checks below were computed with stdlib `csv` + `float()` against `results/oos_predictions.csv` as it sits on disk, not by re-running the generation script. Flagged rather than silently upgraded.

## 1. Row-level OOS genuineness — **Pass**

Grouped the live file by `fold_id` and computed `min(Date)`/`max(Date)`/count per fold directly (not trusting any label): fold 0 → 2011-02-02…2013-09-03 (650 rows), fold 1 → 2013-09-04…2016-04-04 (650), fold 2 → 2016-04-05…2018-10-30 (650), fold 3 → 2018-10-31…2021-06-02 (650), fold 4 → 2021-06-03…2024-01-02 (650), fold 5 → 2024-01-03…2026-08-13 (655). Compared against `E2-S3`'s `fold_boundary_audit.csv` `test_start_date`/`test_end_date` — an artefact generated by a **different script**, re-deriving folds from the canonical dataset independently of this file — and every one of the 6 folds matches exactly, boundary for boundary, row-count for row-count. `fold_id` is not a second, independently-computed label either: `generate_oos_predictions.py::validate_every_row_is_genuine_oos` re-derives the authoritative folds from `splits.py` fresh and asserts every source row's `Date` falls inside the *test set* of the fold it's labelled with (`assert_predictions_trace_to_fold`), which is exactly the split object used to generate the LightGBM training runs, not a second copy — confirmed by import (`from splits import ... purged_walk_forward_splits`, the same module `train_lightgbm.py` imports).

## 2. Uniqueness — one prediction per date — **Pass**

Ran the duplicate check against the live file directly: `len(dates) - len(set(dates)) = 0`. Zero, not "a handful." The policy for the named edge case (overlapping test windows) is not "keep last on concat" or any other silent resolution — `build_canonical_table` **raises `ValueError`** if any duplicate date is found at all (`table.loc[table["Date"].duplicated(keep=False)]`), i.e. the policy is "this must never happen; fail loudly if it does," backed by `test_duplicate_dates_are_rejected` (feeds in a synthetically duplicated row, requires a raise) and structurally reinforced by `splits.py`'s non-overlapping test blocks (previously audited: Pass). There is no accidental "whatever pandas did by default" here — the duplicate path is a deliberate, tested exception, not a merge default.

## 3. No train-set contamination — **Pass**

`generate_oos_predictions.py` does not call `.predict()` itself — it assembles the canonical file from `E2-S2`'s already-generated `lightgbm_oos_predictions.csv`, so the relevant question at *this* stage is whether it could silently admit a train-fold row, and it's guarded explicitly: `validate_every_row_is_genuine_oos` re-derives every fold's `test_idx` from the canonical dataset and requires every row's date to be a member of that set — a training row smuggled into the source file would fail this, not pass silently. `test_concatenation_mismatch_is_rejected` proves this directly: it swaps two rows' dates across a fold boundary (the exact copy-paste-style bug the standard names) and requires the check to raise. As a smell test, not a proof: per-fold `prediction_correlation` (0.045–0.107) and `directional_hit_rate` (0.485–0.601) from `lightgbm_fold_metrics.csv` sit in a consistent, noisy, weak-signal band across all 6 folds — no fold is suspiciously tighter than its neighbours in a way that would suggest an in-sample leak in that fold specifically.

## 4. Null integrity: prediction / actual / regime — **Pass**

Ran an explicit null/blank check against all five columns on the live file: **zero** nulls in `prediction`, `actual_return_5d`, `regime`, `fold_id`, and `Date`. The file's date range (2011-02-02 → 2026-08-13) does not reach the end of the canonical dataset's last realisable-label date — the upstream splitter's `purged_walk_forward_splits` only ever emits `test_idx` for rows where a 5-day-forward label already exists (the canonical dataset itself has exactly 5 trailing unlabelled rows, dropped upstream at `E1-S6`, confirmed by `E4-S1`'s `test_target_horizon_is_not_silently_shifted`), so there is no code path by which a null-actual row could reach this file — consistent with finding zero such rows live. The generation script fails loudly, not silently: `build_canonical_table` raises `ValueError` on any NaN in the three required columns, verified by `test_no_nan_in_required_columns` against the real run.

## 5. Date order preservation — **Pass**

Checked `dates == sorted(dates)` against the live file directly: **True**. The sort is confirmed to be the final assembly step, not a per-fold pre-concat sort: `build_canonical_table` sorts the **already-renamed, fully-selected** dataframe (`table = source_df.rename(...)[OUTPUT_COLUMNS].copy()` then `table.sort_values("Date", ...)`) — i.e. after column selection, before any of the validation raises, and nothing runs between that sort and `table.to_csv(...)` except the validation checks themselves (which don't reorder rows). This is exercised adversarially, not just asserted: `test_shuffled_source_rows_are_still_published_in_date_order` feeds in a `source_df.sample(frac=1.0, random_state=0)` (fully shuffled) and confirms the output is still monotonically ascending — proving the sort is real and not incidentally correct because the source happened to already be ordered.

## 6. Concatenation & index-alignment integrity — **Pass**

No positional/index join exists at this stage at all, which is a stronger property than "joined by key": `prediction`, `actual_return_5d`, `regime`, `fold_id`, and `Date` are not assembled from separate series joined together here — they arrive already bundled, row-for-row, in `E2-S2`'s source file, where they were constructed as a single `pd.DataFrame({...})` literal per fold from arrays all sliced by the identical `fold.test_idx` (confirmed in the prior LightGBM audit's source read of `train_lightgbm.py`), then concatenated with `pd.concat(prediction_rows, ignore_index=True)` — `ignore_index=True` performs the index reset the standard asks for. At the E2-S4 stage itself, `build_canonical_table` only renames and re-sorts this already-aligned frame; it introduces no new join. No parallelised fold execution exists anywhere in this codebase (repo-wide grep for `multiprocessing`, `joblib`, `Pool(`, `ProcessPoolExecutor`: zero hits) — folds are generated by a single sequential `for fold in folds:` loop, so the "worker completion order" failure mode does not apply.

## 7. `regime` and `fold_id` integrity — **Pass**

`regime` values on the live file: exactly `{HighVol, LowVol}` — two values, no case-variant fragmentation (`Bull`/`bull`/`BULL`-style typos), counts 2,216 / 1,689, matching the previously-audited `E4-S1` taxonomy exactly (`{LowVol, HighVol}`, no third label). `regime` is not recomputed at this stage — it is carried through unchanged from the canonical dataset column, which `E4-S1` already verified is look-ahead-safe (`.expanding().median()` guarded by `.shift(1)`, with a non-vacuity counterfactual proving a full-sample version would disagree on 260 rows). `fold_id` distinct values on the live file: `{0, 1, 2, 3, 4, 5}` — exactly 6, contiguous, no stale IDs from an earlier pipeline version and no missing fold, matching `N_FOLDS = 6` and reconciled by `manifest["n_folds"]`.

## 8. Row-count reconciliation — **Pass**

Independently computed the expected row count from `E2-S3`'s `fold_boundary_audit.csv` `n_test` column: `650+650+650+650+650+655 = 3905`. The live file has exactly `3905` rows and `3905` unique dates — an **exact** match, not approximate, and consistent with `oos_predictions_manifest.json`'s recorded `n_rows: 3905, n_unique_dates: 3905`. No dates were excluded for a missing-actual reason (§4 found none to exclude), so no adjustment term was needed in the reconciliation.

## 9. Schema and type validation — **Pass, with one gap disclosed**

Live-file checks: every `Date` value matches `YYYY-MM-DD` (zero non-conforming); every `prediction` and `actual_return_5d` value parses cleanly with Python's `float()` (zero exceptions across all 3,905 rows, including scientific-notation values like `-5.614756859346799e-05`); every `fold_id` is a plain digit string in `{0..5}`; `regime` is a consistent 2-value string set (§7). Column presence/order **is** asserted in code, twice: `validate_source_columns` pins the input to exactly `["fold", "Date", "regime", "y_true", "y_pred"]` and raises on any deviation (e.g. a stray diagnostic column), and `build_canonical_table` separately asserts the *output* is exactly `["Date", "prediction", "actual_return_5d", "regime", "fold_id"]` in that order. **Gap**: I found no explicit dtype-cast-with-assertion for `prediction`/`actual_return_5d` (e.g. an explicit `.astype(float)` plus a check) beyond `pd.to_datetime` on `Date` — correctness today rests on the upstream CSV columns already being numeric when read by `pandas.read_csv`'s type inference, which is currently true (verified above) but is not itself asserted. Minor, not blocking, given the live data is clean and `pandas.read_csv` is deterministic for this file's actual contents.

## 10. Continuity with upstream artefacts — **Pass, with an inherited risk flagged**

The `Date` universe in this file is identical, fold-for-fold, to the OOS date list independently verified in the prior split-parity audit (§1 above — exact boundary match against `E2-S3`'s artefact). `actual_return_5d` is not recomputed at this stage: `test_column_semantics_match_source` confirms `table["actual_return_5d"]` equals `source_df["y_true"]` exactly (same values, just renamed), and `y_true` in the source file is the same `forward_return_5d` target both the baseline and LightGBM evaluations score against. **Inherited risk, not a new E2-S4 defect**: the manifest's `source_predictions_sha256` (`37c82fe6...`) confirms the current file traces to the `E3-S2` pipeline-generated `lightgbm_oos_predictions.csv` — the run the prior audit found was produced by a code path (`pipeline/model.py::run_lightgbm`) that never passes the recorded seed into `LGBMRegressor`. `generate_oos_predictions.py` did exactly its job — it faithfully published what it was given, hash-pinned and traceable — but "faithful" is not the same as "the upstream number is trustworthy"; that defect belongs to the LightGBM stage, not this one, and remains unresolved as of this file's current contents.

## 11. Automated validation as a gate, not a one-off — **Fail (the section that costs this a full Pass)**

The checks themselves are real and run every time the file is *generated*: `generate_oos_predictions.py::run()` raises inline on duplicate dates, non-monotonic order, NaNs, and column-schema mismatches — this is not a manual, one-time audit check, it is baked into the production code path and will refuse to publish a bad file. It is independently re-verified by a second script, `E4-S2/audit_oos_split_integrity.py`, which reads `results/oos_predictions.csv` directly (not the generation script's internals) and reports `oos_table_integrity: {duplicate_dates: 0, in_sample_predictions: 0, fold_traceability: 0, passed: true}` in its own committed `integrity_gate_report.json`. **What's missing**: there is no CI workflow, pre-commit hook, or scheduled job anywhere in this repository (`find` for `.github/workflows/*.yml` and any other CI config: zero hits) that re-runs either script automatically whenever an upstream input changes (a new canonical dataset, a re-trained LightGBM model). Today's clean result depends on a human remembering to re-run `generate_oos_predictions.py` and `audit_oos_split_integrity.py` after such a change — there is no guardrail that would catch drift on the *next* regeneration without that manual step.

## Overall verdict: **Conditional pass**

Per the standard's own bar: duplicate-date policy is fully documented and enforced (§2 is clean, not a gap), and no actual nulls, misalignment, or contamination were found anywhere on the live file — every hard check came back exact and clean, cross-verified against an independently-generated artefact rather than the file's own self-report. The single open item is §11: automated validation exists at the script level (fail-loud on generation, independently re-checked by a separate gate) but is not demonstrated to run unattended on every regeneration.

### What resolves this to a full Pass

1. Wire `generate_oos_predictions.py` and `E4-S2/audit_oos_split_integrity.py` into a CI job or pre-commit/make target that runs automatically whenever `data/processed/E1-S6_canonical_modeling_dataset.csv`, `E2-S2`'s output, or `splits.py` changes — not just when a developer remembers to invoke them.
2. Add an explicit dtype assertion (not just column-presence) for `prediction`/`actual_return_5d`/`fold_id` in `build_canonical_table`, so a future upstream change that yields e.g. object-dtype numbers-as-strings fails loudly here rather than silently propagating.
3. Once the upstream LightGBM seed defect (prior audit, §1) is fixed and the source file is regenerated, re-run this file's own generation and re-verify §10's continuity claim against the corrected source — the current file's row-level mechanics are sound, but its *content* is only as trustworthy as the LightGBM run it was published from.
